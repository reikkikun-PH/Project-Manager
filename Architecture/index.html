The four layers

Everything the app does fits in four shelves, stacked in the order a request travels: someone uses it, they do something, the manager makes it happen, and occasionally an outside service is involved. Pick a role above to dim the parts that role cannot reach.

Layer 1

Who uses it

Three kinds of visitor. The only difference between them is a role, and it is checked afresh on every single action.

Anyone who opens the link

Sees the list of approved projects and nothing else. Every button that would change something is hidden.

Not your role

A signed-in user

Can upload projects, up to two. Each new upload waits for an administrator before anyone else can open it.

Not your role

An administrator

Full control: approve accounts and projects, start and stop apps, lock projects, and see how busy the computer is.

Layer 3

How it works

The machinery. Almost everything passes through the manager — one self-contained program that talks to your computer's operating system and keeps its records in ordinary files.

Keeps everything in files

Accounts, the project list, the project files, passwords and settings are all small files in one folder. There is no database.

Not your role

Runs your apps

Starts each app as its own separate program on its own port, so several can share one computer without colliding.

The manager

Serves the dashboard, decides who may do what, runs and stops apps, serves files, and sends the emails. All in one place.

The three kinds of project

One address, three different jobs. This is the part that surprises people, so it is worth spelling out.

A plain website cheapest

The file is read straight off disk and handed back. No program is started, no port is used, nothing is left running in the background. This is the most reliable kind of hosted project.

Four of the five current projects are of this kind.

An app the manager runs real program

Pressing Run starts a real, separate program — a Python app, a Node app — on its own port, and writes its output to log files. It is told which port to listen on.

Opening the project then passes the request through to that program and brings the answer back. Visitors only ever see /p/verifid/; they never see or need the port.

Each app gets its own port from a reserved block, and the manager's own port is never handed out, so two projects cannot collide on one computer.

VerifID — a face-recognition app with its own models, photos and attendance logs — is the one running this way now.

Anything the app needs to install is set up the first time it starts, which can take a while and needs the internet.

An app you already started yourself bring your own

The same pass-through, but the manager never starts anything — you point it at a port something else is already listening on. Useful for something you run yourself and want on the same address.

Why all three share one address. Each project is mounted under /p/<name>/, and the manager works out which of the three to do from the project list. That is why a link keeps working whether you are on this computer or on the public address — and why links inside a project don't break when you share them.

How the check actually works

The role lens above is a reading aid, not the mechanism. It is worth being precise about what is really doing the work.

Every action is re-checked at the moment it happens the real protection

When you press a button, the manager looks up who you are again, using the account list it holds itself — not anything the page told it. A tampered page, a stale page or a hand-written request all arrive at the same check, and all three are turned away the same way.

This is why the buttons being hidden is a convenience rather than a safeguard. Hiding them makes the dashboard easier to read; refusing the action is what makes it safe.

Signing in does not survive a refresh surprising

The session lives in the page rather than in a cookie, so reloading signs you out and every action is re-checked from scratch. Two browser tabs are two separate sessions: being an administrator in one does nothing for the other.

Locking a project hides buttons, not the site easy to misread

Anyone who already has the address can still open the project. Lock stops the dashboard's controls being used — it is not a way of keeping people off the link. If you need the link itself to be private, that is a different job, and the app will tell you so rather than pretend.

The last administrator cannot be removed deliberate

Neither can the one removing themselves. The guard is on purpose, so the dashboard cannot end up with nobody able to administer it.

One account is the super admin, and cannot be deleted owner

There is one built-in account, superadmin, that comes with the app rather than being created through signup. It is marked Super admin in the accounts list and has no Remove button at all.

No administrator can remove it — not another admin, and not itself. Every other account on the list can be removed by any admin, including other admins; this one cannot be removed by anyone.

The reason is simple: if the last usable admin account could be deleted, there would be nothing left to sign in with and no way to create a new one. The app would be permanently unadministrable, with no way back short of editing files by hand. Keeping exactly one unremovable account means there is always a way in.

The name superadmin and the old admin name are both reserved, so nobody can register them and be mistaken for the real thing. Its password is the documented default until you replace it, which is worth doing early — it is the one account you cannot revoke by removing it.

Passwords are stored as plain text. Anyone who can read the accounts file can sign in as anyone, which is exactly why the check above has to be re-done every time rather than trusted once at sign-in. Keep the folder private, and don't reuse a password you use elsewhere — see what to back up.

Creating an account

Two different routes in, because the two roles need proving in two different ways. A person only ever goes through one of them.

A user confirms their own email with a code no approval

Every account needs an email address — a user included. When someone signs up as a user, a six-digit code is emailed to the address they gave and they type it in.

That is the entire approval process. No administrator is asked, and none is waiting. Until the code comes back the account exists but cannot sign in — which is the point. Without this, anyone could register using an address they do not own.

The code stops working after ten minutes, and five wrong guesses void it so nobody can simply keep guessing. There is a one-minute wait between sending codes, and a cap of five an hour, so the address cannot be flooded.

If the code does not arrive, the screen says so plainly and offers to send another — it never pretends a message went out when it did not.

An admin request waits for a person approval

An admin request is not confirmed by code. Its address is already required — it is how the decision reaches the applicant — but a code would prove nothing extra, because the real question is whether this person should be allowed to administer the app at all. That is a human judgement, so it goes to the ACCOUNTS card and waits there as PENDING.

Being unable to receive the code does not help someone get admin access, so asking for one would be security theatre.

Unverified is not the same as pending. In the accounts list an UNVERIFIED row means nobody is holding this up — the person just has not typed their code yet. A PENDING row means a human has to act. So unverified rows are not counted as things waiting for you, and they have no Approve button: approving one would hand out a working account for an address nobody proved they own. They can still be deleted, so an abandoned sign-up does not sit there holding a username forever.
